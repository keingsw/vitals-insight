# ADR-001: リポジトリの構成とパッケージマネージャー

- ステータス: 承認 <!-- 提案中 | 承認 | 置き換え(ADR-NNN) -->
- 日付: 2026-11-07

## 背景

- vitals-insight は SDK、ダッシュボード、インフラ、デモサイト、API、集計 Lambda から成る
- SDK が送るイベントの形式は API と集計 Lambda が共有し、形式を変えるとそのすべてに影響する
- SDK は npm で配布し、API、ダッシュボード、集計 Lambda は AWS にデプロイする。そのため本番には新旧の SDK のイベントが届く(具体的な配布方法は第6週に検討する)
- 開発者は1人で、使える時間は週4時間
- 宣言していないパッケージを import できないようにしたい
- CI などでロックファイルが書き換わったり、予期しないパッケージがインストールされたりするのを防ぎたい
- サプライチェーン対策として、公開から14日未満のパッケージをインストールできないようにしたい
- サプライチェーン対策として、依存パッケージのインストールスクリプトは、明示的に許可しない限り実行できないようにしたい

## 決定

- モノレポ構成にする
  - npm 公開と AWS デプロイの権限は GitHub Actions の Environments で分け、本番環境のシークレットは main からのみ利用できるようにする
- パッケージマネージャーは pnpm にする
  - pnpm は、公開から14日経過した最新バージョンを使う(2026-11-07 時点では v12.15.0)
  - `minimumReleaseAge` を 20160(14日)に設定する。緊急度の高い脆弱性の修正は、バージョンを指定して `minimumReleaseAgeExclude` に追加し、14日後に外す Issue を立てて管理する
  - 信頼できるパッケージだけを `allowBuilds` に追加し、ビルドスクリプトの実行を許可する
  - CI では `--frozen-lockfile` を付けて依存をインストールする
  - ワークスペースルートの `package.json` にはランタイムの依存を置かない

## 検討した代替案

### リポジトリの構成

| 案 | イベントの型の共有 | 影響範囲の確認 | 配布の違いへの対応(バージョンとタグの管理、CI の絞り込み) | 開発者1人にかかる運用の手間 | 権限の分離 | 選ばなかった理由 |
| --- | --- | --- | --- | --- | --- | --- |
| モノレポ | 型定義のパッケージを依存に含めて共有できる | ・1つの PR で変更できる<br>・変更による不具合に PR の段階で気づける<br>※ どちらの案でも、旧バージョンとの互換性は、旧形式のイベントのサンプルを API に通す回帰テストなどで別途保証する必要がある | ・パッケージごとにバージョンとタグの管理が必要<br>・関係のないパッケージの deploy や publish が起きないよう、CI で対象ファイルを絞り込む必要がある。依存先の変更も対象に含める必要があるが、抜けやすい<br>・npm で配布する際は、依存を含めてビルドするか、依存のパッケージも npm で配布する必要がある | 1つのリポジトリで作業が完結し、切り替えの手間がない | npm 公開と AWS デプロイの権限が同じ場所に置かれるため、CI が侵害されると被害範囲が広がりやすく、調査も大変になる。Environments でシークレットを分けるなどの工夫が必要 | (採用) |
| 複数リポジトリ | ・型定義のパッケージを npm で公開し、依存に含めて共有できる<br>・公開から14日未満のパッケージはインストールしない方針なので、公開後に待ち時間が発生する<br>・`minimumReleaseAgeExclude` などで除外すれば回避できるが、アップグレード作業は毎回必要 | 影響範囲を通しで確認できない。利用側でパッケージをアップグレードするまで不具合に気づけない | 対象が単一のパッケージなので、バージョンとタグの管理も CI の設定もシンプル | 複数のリポジトリで PR を作る、開発環境を立ち上げる、パッケージを npm 経由で共有するなど、作業が複雑で時間がかかる | リポジトリごとに権限を独立して管理できる | 限られた時間で開発を進めるには、開発効率を高く保ちたい。次の点で複数リポジトリは劣る<br>・リポジトリの往復と、変更のたびの配布とアップグレードで、開発スピードが落ちる<br>・不具合の発見が遅くなりやすい<br>・切り戻しはどちらの案でも影響範囲によって複雑になりうるが、複数のリポジトリで PR を作る分、時間がかかる |

### パッケージマネージャー

| 案 | 宣言していないパッケージの import | CI での lockfile の固定 | 公開から14日未満のバージョン | install スクリプトの既定 | 選ばなかった理由 |
| --- | --- | --- | --- | --- | --- |
| pnpm | `package.json` に宣言していないパッケージは import できない。ただし、ワークスペースルートの `package.json` の依存は import できる | 可能。`--frozen-lockfile` を使う | ・`minimumReleaseAge` を指定し、`minimumReleaseAgeStrict` が true である限りインストールできない(`minimumReleaseAge` を指定すると、`minimumReleaseAgeStrict` の既定は true になる)<br>・`minimumReleaseAgeExclude` で例外を設定できる | 依存のビルドスクリプトは既定で実行されない。`allowBuilds` でパッケージごとに明示的に許可する | (採用) |
| Bun | isolated installs により、`package.json` に宣言していないパッケージは import できない。ただし、ワークスペースルートの `package.json` の依存は import できる。isolated installs は `configVersion` が1なら既定で有効で、それ以外は明示的な設定が必要 | 可能。`--frozen-lockfile` を使う | ・`minimumReleaseAge` を指定するとインストールできない<br>・`minimumReleaseAgeExcludes` で例外を設定できる | Bun が既定で許可しているパッケージのビルドスクリプトは実行される。すべて防ぐには、`trustedDependencies` に空配列を明示的に設定する | install スクリプトの既定が pnpm より緩い。`trustedDependencies` の設定だけなので対応は軽いが、設定を忘れても安全な側に倒れる pnpm を選ぶ |
| npm | hoisting により、宣言していないパッケージも import できる | 可能。`npm ci` を使う | ・`min-release-age` を指定するとインストールできない<br>・`min-release-age-exclude` で例外を設定できる | v12 から、依存のビルドスクリプトは既定で実行されない。`allowScripts` でパッケージごとに明示的に許可する | 宣言していないパッケージを import できる |

## トレードオフ

- 得る:
  - イベントの型を直接共有できる
  - 1つの PR で影響範囲を確認できる
- 払う:
  - npm 公開と AWS デプロイの権限が同じリポジトリに同居する
  - パッケージごとのバージョンとタグの管理が必要になる
  - CI で対象ファイルを絞り込む必要がある
  - 14日待つので、脆弱性の修正もすぐには入らない
  - eng-lab は Bun を使っているため、2つのパッケージマネージャーの設定とバージョンを管理する必要がある

## 見直す条件

- `minimumReleaseAgeExclude` に入れた緊急の例外が四半期に5件を超えたら、14日という値を見直す
- CI の絞り込みの抜けで、壊れた変更が main に入ることが2回起きたら、CI の対象を依存関係から計算する方式に変える
- 外部のコントリビューターが入り、Environments では不十分になったら、リポジトリの分割を再検討する
